# 兵线与中途拦截

玩家的持续兵线表示逻辑意图，例如 A → D。敌方控制区仍然生效，单位可能需要依次占领 B、C 才能到达 D，但 B、C 不再被自动写入持续兵线或“占领后继续行动”命令。

## 内核状态

- `SiteState.orderTarget`、`orderOwner`：原始持续兵线。
- `plannedOrderTargets`：明确设置的占领后兵线，系统中途拦截不再使用这个字段。
- `UnitState.movementOrder`：单位的最终目标、命令所属阵营，以及玩家持续兵线的来源据点。
- `UnitState.targetSiteId`：当前实际行进或攻击的中途目标。

单位到达中途据点后，继续执行自己的目标，不招募该点其他部队，也不覆盖其他经过这里的命令。取消原兵线会停止归属于它的在途命令；单独下给单位的命令与原兵线解绑。改变兵线目标、来源据点失守、单位变更阵营、撤退和目标被摧毁均有对应处理。

旧存档缺少兵线归属标记时，按内核控制的阵营补全。旧自动后续路线可由复制自其他来源据点的路径或 AI 归属识别并迁移；明确从本点出发的后续路线保留。无法确定来源的历史信息不能凭空恢复。

## 预览中兵线消失的原因

此前 UI 预览启动的是 `work/e2e-plugin/qingbei-server.exe`，该文件构建时间为 2026-09-01，二进制既不包含当前 `kernel_bundle.js`，也没有 `orderOwner` 字段。这使旧生产周期清理逻辑仍在运行。此后必须使用重新构建的服务器，而不能只更新插件。

运行实例的 `/api/info` 返回 `kernel.orderRulesVersion: 1` 表示包含这一版命令规则。Go 内嵌内核健康测试也要求该字段，缺失会提示先执行 `npm run build:kernel`。

## 验证

`npm run test:orders` 覆盖连续拦截、两条兵线共用中途点、取消与改目标、显式占领后命令、双方十个游戏日的持续增援、保存恢复、旧存档迁移与来源归属。原生运行时另有多日生产周期测试，验证实际内嵌 JS 行为。

AI 矩阵沿用原有验收阈值，没有放宽断言。当前仍有一项未通过：`thu-standard-idle` 伤亡为 1634 / 1405，比例约 1.163，高于 1.1。其余现有断言通过；困难 AI 对静止对手约在8月23日取胜，也早于历史偏好的8月25日下界（该偏好未编码为矩阵断言）。这是待处理的 AI 平衡问题，不能把本次命令修复宣称为完整发布验收通过。

命令专项、TypeScript 检查、网页构建、Go 服务端及插件测试通过。最终本地服务器使用重新构建的 `v0.3.5` 二进制，并验证其中嵌入的 JS 字节与源码构建产物完全一致；运行时 `/api/info` 的 `kernel.orderRulesVersion` 为 1。

## 联机决策取消

另一个已定位的问题是原客户端取消决策仅清空本地状态、增加本地资源，没有发送联机动作，因此服务器会重新同步仍在进行的决策。现已增加 `decision_cancel`，由认证连接决定阵营，内核校验决策ID、开始时间及持久化的实例编号后取消并退还50%资源。重复请求、已完成决策和旧实例请求不会再退款；同一游戏时刻重新开始同一个决策也有不同实例编号。

插件为线上旧客户端资源适配取消按钮，不依赖立即发布通用网页。运行时 `kernel.decisionCancellation: true` 可用于确认服务端支持。`npm run test:decisions` 和原生宿主测试覆盖完整动作、状态同步、同帧重开、防重退款及跨阵营请求。

浏览器实测取消了80资源的“校务公开”：服务器资源从180变为220，当前决策清空，取消按钮随权威状态消失；刷新重连后仍无进行中决策。最新验证实例为本地17941端口，旧预览端口不会自动获得新内核。
